# M3.2 concrete implementation proposal — NOT implemented

Prepared after the focused M3.1 acceptance review. This document authorizes no code,
deployment, migration, mail dispatch or feature change. The current branch contains
M3.1 corrections only. Every identifier below is a proposed M3.2 contract.

## Scope and order

1. Freeze these contracts and privacy/abuse/key-handling decisions.
2. Add capability/challenge/outbox/limit tables and narrow RPCs; preserve M3.1 interlock.
3. Add owner-only non-PII form approval/binding through existing governance confirmation.
4. Implement sanitized mail/outbox adapter and leased mail worker, initially synthetic.
5. Implement deliberate email exchange, recovery and server-side sessions.
6. Implement partial draft saving, explicit rebase, cancellation/recovery of uncertain saves.
7. Implement three role wizards under a private layout; no upload or submission control.
8. Run database/API/UI/browser/negative/regression acceptance; stop for phase review.

Use existing unified Supabase, Node handlers, React/Zod/UI primitives and Resend.
No Auth applicant, new identity provider, global applicant directory, pool intake,
document upload, malware integration, submission, interview, decision or activation.
M3.3 adds actual documents; M3.4 final submission; M3.5 staff/pool; M3.6 operational
retention/rights/restore readiness. No real collection before those launch dependencies.

## Dependencies and existing foundation reuse

Requires M1/M2, original M3.1 and the acceptance correction in that order. Reuse exact
form/scope/version/publication FKs, private contacts, versioned payloads, case requests,
consent, coded case audit and locks. Reuse staff provider validation/MFA for OWNER
FORM GOVERNANCE only. Do not use M1 journals or Auth users for applicant operations.

M3.1's normalized-email unique indexes enforce one active email/vacancy across HMAC
rotation. New RPCs create case+contact+first payload+notice evidence+session atomically.
Existing active case is resumed only after proof; unverified initiation never reveals it.
Retained inactive case requires independent owner reapplication approval. M3.2 denies
unapproved replacement rather than inventing a self-service owner bypass. A future
case-management operation can provide that approval. Erasure does not keep email forever.

## Database additions: four tables, no new applicant identity table

All have RLS, no browser/direct service table grants and empty-search-path narrow RPCs.
No anonymous function execution. Service RPCs validate capability/proof independently;
worker routes also require a separately authorized operational credential.

### recruitment_email_challenges

UUID PK; intent_group UUID; initiation request UUID/digest; action begin/recover;
purpose vacancy/talent_pool (pool execution unavailable in M3.2); nullable case FK
ON DELETE CASCADE; exact scope/vacancy/version/publication/form pins; normalized email;
purpose HMAC and key version; email_revision; accepted notice version; adult affirmation;
unique 64-hex SHA-256 proof hash; created/proof_expires/intent_expires timestamps;
bounded attempts; consumed/revoked timestamps. No raw proof outside encrypted mail.

CHECKs enforce purpose pins, adult=true, finite lifetimes, proof <=15 minutes and
unverified intent <=24 hours. Composite FKs mirror forms/publications. Recovery case
and contact must agree at execution; email revision is runtime-checked, not an FK that
would prevent revoking old sessions when contact revision changes. Index proof hash,
context/email HMAC, intent group, expiry and active intents. Unique initiation request
rejects changed reuse without revealing candidate existence.

Anonymous resends must not invalidate a still-valid legitimate proof. Permit at most
three live proofs per purpose/context, each independently rate-limited. One successful
exchange revokes sibling proofs under the case/context lock. No endless resend renewal.

### recruitment_applicant_sessions

UUID PK; case FK CASCADE; unique 64-hex SHA-256 capability hash; email_revision;
kind applicant/privacy; server-derived allowed_actions; created/last_seen/idle_expires/
absolute_expires timestamps; revoked_at; optional predecessor self-FK SET NULL.
No Auth UUID and no raw cookie. CHECK idle<=absolute, finite expiry, privacy actions
exclude answer writes/rebase/upload/submit. Index hash, case and expiry. Partial unique
case index WHERE revoked_at IS NULL; revoke old/expired rows before minting a replacement.
Do not use volatile now() in a partial-index predicate.

Idle30 minutes, absolute24 hours. Same-session rotation carries the absolute cutoff;
fresh verified recovery may establish a new session but never renews draft retention.
Every access joins the current contact email revision and case state/retention.

### recruitment_email_outbox

UUID PK; nullable case/challenge FKs CASCADE; intent/purpose/template; unique logical
message/idempotency key; status pending/claimed/sent/failed/cancelled; AES-256-GCM envelope
BYTEA, nonce12 bytes, tag16 bytes, encryption key version; created/expires/available_at;
claim UUID/lease_until; attempts; provider reference; sanitized error code.
Envelope contains recipient and proof only until dispatch/expiry; no plaintext body
archive. The encryption key is outside the row and separate from lookup/digest keys.
Index due available jobs and expired leases. Verification mail must expire with its
proof; unverified operational records/envelopes expire within24 hours. Scrub ciphertext,
nonce and tag immediately after accepted delivery or expiry. Provider metadata is
pseudonymous, not a reason for indefinite retention.

### recruitment_intake_limits

PK(key_hash,window_start,window_seconds); HMAC key version; coded action/dimension;
attempt count; finite expires_at. No raw email/IP. Index expiry. Counter TTL<=24 hours.
Required because M1 counters have fixed15-minute semantics and max30 attempts, and
must not have their staff-auth capacity consumed/changed by public traffic. This is
an operational abuse boundary, not another applicant/business identity table.

## Small necessary extensions to existing requests

Add digest_key_version to recruitment_case_requests so keyed canonical digests remain
verifiable across rotation. Old accepted request keys must remain available for their
approved replay lifetime. Do not couple that key to contacts.key_version.

Add cancelled terminal request state and cancel_pending operation, plus a coded audit
action for cancellation. Preserve immutable request identity and committed/cancelled
outcomes. This permits safe reload recovery WITHOUT storing sensitive pending answers:
under the case lock, cancellation either returns an already committed original result
or inserts a cancellation tombstone for the original request ID. A later arriving
original request must reject the tombstone. Cancellation itself has a stable request
ID and metadata digest. It can cancel only this case/principal's uncommitted save/rebase,
never undo committed data. No new table is needed. These changes are proposed, not
part of the M3.1 correction.

## Proof and session protocol

- Begin requires approved public form, adult affirmation and privacy acknowledgement;
  only a short-lived intent exists before email proof. Return generic202 accepted=true.
- Random256-bit one-use proof; hash validation; link uses fragment, never email/query
  bearer. Clear fragment immediately before rendering/analytics. GET does not consume.
- Inspect is a read-only POST of proof/intent returning masked email, role/purpose and
  expiry, never answers or existing-case status. Exchange requires deliberate confirm
  plus re-entered full recipient email matching the proof. This reduces login-CSRF and
  works across devices; a browser nonce is supplementary, not an undocumented account.
- Exchange checks proof, current notice/form/publication/deadline and locks. A stale
  pre-draft form is rejected; applicant rereads requirements/reinitiates. Existing
  active drafts require explicit rebase instead of silent interpretation.
- Server generates raw session token; DB receives only its hash. Cookie:
  `__Secure-viva_recruitment_applicant`; Secure,HttpOnly,SameSite=Strict, host-only,
  Path=/api/recruitment; never Domain. Do not use __Host- with a non-root Path.
- Recovery: email+case reference or known vacancy context; generic202 regardless of
  existence. Fresh case-specific proof rotates/revokes old sessions. Different case
  reference or knowing a UUID never authenticates. Email change is out of M3.2 scope.
- Only one current browser cookie/case. Switching cases is explicit; no token map in
  browser storage. Other tabs receive a safe mismatch rather than another case's data.
- If exchange commits but Set-Cookie/response is lost, never replay a consumed proof
  to mint another session. Use existing cookie if delivered or fresh email recovery;
  active uniqueness prevents a duplicate case. A valid already-issued session can
  recover metadata without resurrecting the proof.
- Rotation sets a cookie only when that transaction actually accepted the newly
  generated hash. An authorized replay returns metadata without issuing a fresh
  unrecorded cookie; if the original replacement cookie was lost, use email recovery.
- Intake off/closed vacancy: existing authorized own-case reads remain permitted
  while retained; no new write capability. Recovery may grant read/privacy-only
  authority, never restore intake. Withdrawn/deletion cases get privacy-only status.
  Mail disabled/unavailable means no promise of a fresh link: independently verified
  controller process, never relaxed ownership checks.

PATCH: omitted key means unchanged; null explicitly removes a field from the draft;
merge under lock then validate full resulting partial answers. No editable email,
verification, scope, status, age-policy or authority metadata. Max raw envelope70 KiB;
answer representation<=64 KiB plus existing per-field limits. Outgoing errors include
{error:{code,message,fieldErrors?},requestId?}; field errors contain keys/codes, not
rejected values/provider diagnostics. Other bodies max4 KiB; worker body max1 KiB.

Errors:400 invalid_request;401 verification_required/invalid_proof;403 access_denied;
404 case_unavailable;409 revision_conflict/requirements_changed/request_conflict/
request_cancelled/controlled_reapplication_required;413 answers_too_large;
429 rate_limited (Retry-After);503 intake_disabled/mail_unavailable. Per-email
suppression still returns202 to avoid enumeration; IP/global limits may return429.

Those actions must be rejected, not accepted as successful placeholders. M2 public

Notice content must come from an explicitly approved versioned policy catalogue, not
an arbitrary URL/body or the existing generic site policy by assumption. No fallback
evidence duration when case_evidence_days is NULL. The M3.1 interlock remains installed.

## Transactions, idempotency and meaningful activity

Lock settings FOR SHARE → vacancy FOR SHARE → case → session/contact → payload,
compatible with M2's update order. Check clock_timestamp after waits; no email call
inside locks. Exchange first reads (but does not lock/consume) the proof to identify
context. Lock an existing case, or create case/contact inside a subtransaction protected
by normalized-email uniqueness. A losing unique insert rolls back that tentative case,
then locks the winner. Only then lock/revalidate/consume the challenge and revoke
siblings in deterministic order. No exchanger holds its own proof while waiting on
another transaction's case/contact uniqueness; this avoids a sibling-revocation deadlock.
Invalid/expired proof at the final check rolls back all tentative case/contact data.

Each meaningful save appends a payload revision; never mutate an older payload used
as a request result. Update case revision/activity/audit/request in the same transaction.
Unchanged saves can return a no-change result without renewing14 days. Replay validates
current capability before lookup and returns original payload revision; it does not
renew activity or depend on a rotating session identity. HMAC canonical command includes
operation/revision/patch/form, excludes credentials, and records digest key version.

Conflicting revision returns409; no silent overwrite/merge. Keep original UUID through
transport uncertainty; do not classify an intermediary response or later401 as proof
of noncommit. Persist ONLY opaque pending UUID+operation with short TTL, never answers,
files, email, case token or proof. After reload: authorized status lookup; if not committed
and original payload is lost, explicit cancel_pending under case lock before a newly
  confirmed save. No automatic consequential retry with a fresh ID.

Do not prune request/cancellation evidence while its case remains active: stored expiry
is a cleanup candidate, not permission to reuse an ID. Recheck current case retention,
extensions and holds; keep digest key versions for the supported replay lifetime.

## Email adapter and failure recovery

Keep Resend/sender infrastructure, but a separate recruitment adapter must not require
ADMIN_EMAIL or log provider bodies. Templates verification/recovery only in this phase;
no CV/answer attachments, signed document links or staff recommendations. AES-GCM envelope
key is separate from lookup, request-digest and abuse HMAC keys, with explicit key versions.

Claim due mail with SKIP LOCKED, bounded leases and unique provider idempotency key.
Recheck current challenge expiry/revocation and mail gate immediately before dispatch.
Retry transient failures with15/60/180-second backoff within proof TTL; permanent or
expired failures stop, scrub and show generic recoverable state. Provider idempotency
window must be accepted; uncertain sends outside that window are reconciled, not blindly
resent. Mail HTTP request occurs after claim commit, not while case rows are locked.

M3.2 adds short-lived auth/mail cleanup but not full case erasure. Full approved deletion,
holds, rights, backup reconciliation, scanner and operational acceptance remain launch
gates. Evidence policy NULL never falls back to90 days. Positive local tests may replace
the interlock ONLY inside isolated synthetic SQL fixtures; no environment bypass,
production flag change or application backdoor.

## Acceptance tests and stop gates

- Exact DDL/FKs/RLS/grants; accountless create; one email/vacancy under concurrent proof
  exchange; creation rollback leaves no orphan; HMAC/key rotation duplicate/replay safety.
- One-use purpose/email-revision/expiry binding; no GET consumption; masked metadata;
  wrong-confirmed-email/login-CSRF; consumed proof after lost response cannot mint again.
- Actual cookie path/host/SameSite/Secure behavior; no staff/learning-cookie substitution;
  cross-case/expired/revoked/session-rotation isolation and own logout.
- Partial/unknown/role-specific/adult/schema validation; complete values remain false
  for whitespace; immutable form/version pins; explicit rebase and fresh notice consent.
- Revision/multi-tab conflicts; no-change saves do not renew; lost response/reload retains
  UUID only; cancellation versus late save returns committed original OR blocks it;
  no automatic new-ID operations; permission checks before replay after closure/recovery.
- Generic email enumeration/rate/cooldown/queue/cost limits; fake provider errors contain
  no PII/token; envelope scrubbing/lease expiry/provider-idempotency and mail-off behavior.
- Privacy route direct load AND navigation from public page with analytics configured:
  no GA/embed/click telemetry, fragment/referrer leakage, cached PII or browser persistence.
- All three wizards at mobile/desktop; keyboard/focus/errors; selected axe checks; no
  apparent upload/submit/talent-pool form that accepts unavailable actions.
- Full existing M1/M2/enrollment/academic/teaching/accounting regression, both TypeScript
  checks, lint/build. Real Supabase/Resend/cookies/contention acceptance reported separately.

Rollback: transaction rollback before commit; later leave gates/interlock off and forward
fix, preserve recover/privacy semantics and evidence. Never drop applicant data to roll
back or restore old migration bundles over corrections. No public intake until approved
privacy notice/retention/evidence, full erasure/restore readiness and explicit rollout.
Stop after M3.2 verification/report; do not start M3.3 without its review gate.
