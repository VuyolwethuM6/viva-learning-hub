# Implemented M3.2–M3.6 contracts

Current code contract; earlier technical-design and phase documents describe design history. All public rollout remains disabled. This is a single additive release dependent on corrected M3.1/M2; apply all four new migrations before serving these routes.

## HTTP contract

Public/private applicant routes use one existing-convention action router: `/api/recruitment?route=...`. All responses are no-store, no-referrer, nosniff, noindex; JSON writes require same-origin. Applicants use only the dedicated HttpOnly SameSite=Strict capability cookie, Secure in hosted deployments, Path=/api/recruitment. No Supabase Auth applicant account, localStorage credential, bearer token in a URL, or shared staff session is introduced. Route query parameters carry only public slugs, bounded filters or opaque identifiers. Staff PII searches use POST bodies.

All mutation UUIDs are generated once per reviewed operation. For applicant command bodies the server HMAC signs canonical metadata and payload; retries use the recorded key version. Case requests bind a stable case principal rather than a rotating session. Browser sessionStorage holds only an opaque request UUID and operation name; no answers, filenames, proofs, codes or credentials. Reload checks request status before another action. A cancellation tombstone is created under the case lock if an uncertain operation is not recorded, so a late original cannot execute after the user reviews a replacement. Staff case recovery waits for the exact proof to expire if no committed result is known. Never automatically retry consequential commands under new IDs.

| GET `route=policy` | Approved privacy notice/version for recovery, independent of an open vacancy; email/readiness gates still apply. |
| POST `route=email` begin/resend/recover | `{action,requestId,purpose,slug,email,noticeVersion,privacyAcknowledged:true,adultConfirmed:true,caseReference:""|uuid}`. Generic 202 `{accepted:true}` for eligible/ineligible existing identity contexts. Strict normalized email, notice/version, adult affirmation, bounded slug and purpose. Request an email, never create an application before proof exchange. |
| POST `route=email` inspect | `{action:"inspect",intentReference,proof}`. Masked address, purpose and expiry only. Does not consume proof. |
| POST `route=email` exchange | `{action:"exchange",intentReference,proof,confirmedEmail,confirmation:true}`. One-use 15-minute 256-bit proof, full email/purpose binding, email revision; returns reference/revision/kind and sets fresh case cookie. Recovery revokes previous sessions. A lost exchange response requires cookie/status inspection or a fresh recovery email, never recovery of a raw capability from storage. |
| GET `route=applicant&requestId=optionalUUID` | Own current case/reference/state/revision, pinned form/notice, answers, current document statuses, receipt and applicant-visible clarification/replies. | POST applicant, action rebase | `{action,requestId,expectedRevision,formId,noticeVersion,privacyAcknowledged:true}`. Explicitly accept current form/notice. Carry only currently valid answers; retain compatible document requirements/policy, discard incompatible ones. Cannot alter sealed submitted requirements. |

| POST applicant, action submit | `{action,requestId,expectedRevision,formId,privacyAcknowledged:true,poolConsent:boolean}`. Require complete approved answers/adult affirmation, exact current publication/form, open deadline and all attached documents clean under accepted scanner policy. Pool consent must be true for pool cases. One transaction seals new payload + manifest + receipt + audit + outbox. Returns `{receipt,submittedAt,replayed}`. |
| POST applicant, action reply | `{action,requestId,expectedRevision,replyTo,text}`. Max 4,000 characters; own active submitted case and an applicant-visible clarification only. Separate append-only message, no sealed answer changes. |
| POST applicant, action withdraw/request_deletion | `{action,requestId,expectedRevision,formId:null,noticeVersion:"",consent:false}`. Own privacy authority, revision/idempotency, hold-aware erasure; pending jobs cancelled. Retention is not contingent on public intake remaining open. |
| POST applicant, action renew | Same privacy metadata plus current `formId,noticeVersion,consent:true`. Pool only, submitted/active, current compatible approved requirements, fresh email session within 15 minutes, new 12-month affirmative consent record. |
| POST applicant, action reapply | Same privacy metadata plus current form/notice/consent. A different eligible owner must have explicitly authorized the inactive vacancy case, within a bounded authorization window. Fresh verification within 15 minutes; unique active email/vacancy invariant; new case and capability, no inherited hiring/system access. |
| DELETE applicant | Revoke dedicated applicant session and clear its cookie. Staff/general portals remain separate. |
| POST `route=documents`, action reserve | `{action,requestId,requirementKey,name,size,checksum}`. Verified draft, approved requirement, live scanner health/attestation and private/RLS Storage configuration; PDF-only 10 MiB, 8-file/40 MiB cap. Returns `{documentId,generation,chunks,size}`. |
| POST documents, action chunk | `{action,documentId,generation,index,data}`. Base64 2 MiB maximum, indexes 0–4 and exact final-part length. DB-authorized immutable quarantine path; checksum checked before and after storage, no overwrite. Repeating exact bytes is safe. |
| POST documents, action finalize/discard | `{action,documentId,generation}`. Finalization requires all committed exact chunks and queues a leased scan. Discard invalidates generation access, cancels scanning and schedules grace-based cleanup. Interrupted uploads can be discarded and reselected; no private file is browser-persisted. |
| GET documents `documentId&part=0..4` | Recheck own current clean file authorization on every part, verify complete stored SHA/size, return bounded part as attachment with no-store/nosniff. No signed/public URL. |
| POST `route=worker` | Separate server-only bearer; `{action:"mail"|"scan"|"retention",limit:1..10}`. Fixed command set, no arbitrary SQL, principal or bucket path. Workers lease and revalidate jobs, fail closed and return sanitized counters. No cron deployed. |

General API budget: 120 requests/IP/minute. Email jobs additionally commit HMAC-only limits of 20/IP/15min, 3/email-context/hour, 500 globally/day and 60-second context cooldown. Draft commands: 300/case/hour. Staff staging: 20/actor/minute; searches: 60/actor/minute. Existing M1 fresh-auth budgets also apply. Configure trusted proxy and edge controls before hosted enablement; counters cannot replace edge denial-of-service protection.

Errors are JSON `{error:{code,message}}`, never provider/SQL/body diagnostics. Confirmed business 4xx carry `X-Recruitment-Error: confirmed`; transport errors, malformed intermediaries and 5xx are uncertain. Important codes: invalid_request 400, verification_required/invalid_proof 401, access_denied/mfa_required 403, case_unavailable/form_unavailable 404, revision_conflict/requirements_changed/request_conflict/request_cancelled/application_incomplete/documents_not_clean/applications_closed 409, document_quota 413, rate_limited 429, intake_disabled/scanner_unavailable/privacy_policy_unapproved/service_unavailable 503. Unknown safe SQL business codes remain sanitized 400; infrastructure errors are uncertain 503.

## Recruitment staff APIs

Existing `/api/admin/recruitment?route=...`, dedicated validated recruitment Auth session, current verified role, fresh password and configured owner AAL2, no broad Admin fallback. GET forms is owner-only. GET applications lists authorized submitted cases (kind/cursor only) or reads one `caseId`. POST applications accepts `{search,kind,after?,afterId?}`; no PII in query strings. Detail includes pinned human answers, authorized clean documents, notes, assignments, eligible scoped staff and case audit. Officers receive no delegation directory. GET privacy uses opaque case reference and independent owner authority, minimal metadata and holds; it does not grant ordinary ended-case access.

Case changes use POST case-stage (notes/clarifications/recommendations only), case-reauthenticate, case-mutate and GET case-recover. Staged text stays in short-lived case buffers, never the M1 request journal. Case-reauthenticate takes `{operation,data,password,factorId?,code?,keyVersion?}`, validates current Supabase identity, rotates session, clones staged content into that session and returns `{data,proof,keyVersion}`. Case-mutate uses that exact data/proof/version; DB checks actor, scope, case assignment, conflict, revision, proof and request digest again under locks. Released operations: assign, revoke_assignment, note, clarify, recommend, declare_conflict, hold, extend_retention, resolve_conflict, reapply. GET case-documents uses current scoped document permission and owner assurance. POST case-step-up refreshes owner assurance for private reads. Credentials/proofs never persist in browser storage.

Owner: independent organization-wide submitted review, form/privacy approval, case assignment and privacy governance. Manager: current scope + explicit case assignment; human review and in-scope delegation. Officer: current scope + explicit case assignment, read/document/review only. No role may read private draft answers, review its own matching/declared case, resolve its own conflict or inherit teaching/general Admin access. Revocation continues to work for unverified/disabled targets. Final hiring/rejection/interviews/offers/onboarding/activation and compensation processing are absent.

M1 owner-confirmed operations extended only with `intake_policy`, `intake_form_approve`, `intake_form_bind`. Approved forms derive solely from reviewed SQL/TypeScript templates and an exact approved vacancy version, preserving tutor/administrator/support boundaries. Talent-pool approval creates/reuses its dedicated recruitment scope atomically. All five flags and mandatory-access controls preserve existing M1/M3.1 enforcement.

## New database entities

All 12 new tables use RLS, with all direct public/anon/authenticated/service_role table privileges revoked. Only enumerated security-definer RPCs have service-role EXECUTE. Internal helpers and operator export/restore/attestation have no service/browser grant; all functions fix search_path. Existing 13 foundation tables remain authoritative, now 25 total.

Foundation additions: current_payload_id + deferred case/payload FK; versioned request digest/cancelled tombstones; immutable draft snapshots; operational policy/scanner/backup attestations; new reviewed audit/proof operation sets; note buffers tied to fresh sessions; explicit reapplication authority/expiry/consumption; consent form pin for renewals. Existing composite cross-case/vacancy/publication constraints, HMAC-independent normalized-email uniqueness, sticky conflicts, retention/hold barriers and all five false flag CHECK constraints remain enforced. A restrictive Storage policy affects only the two new buckets, leaving legacy bucket predicates unchanged.

Case notes and applicant-visible clarification/reply messages use 50-row keyset pages, with a 51st-row hasMore check. GET applicant `route=messages&before=ISO&beforeId=UUID` and staff `route=case-messages&caseId=UUID&before=ISO&beforeId=UUID` recheck current capability or role/scope/conflict/assurance before every page. Internal notes are excluded from the applicant query before pagination.
